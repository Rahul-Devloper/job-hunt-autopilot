# Database Migrations

The database schema is version-controlled via Supabase CLI migrations in
`supabase/migrations/`. This is the source of truth — schema changes go
through migration files, not ad-hoc SQL run directly in the Supabase
dashboard.

The baseline migration (`supabase/migrations/20260727122900_remote_schema.sql`)
was generated by introspecting the live production schema on 2026-07-27 and
captures everything that existed before migrations were tracked: all tables,
columns, constraints, enums, indexes, foreign keys, and RLS policies.

## Prerequisites

- [Supabase CLI](https://supabase.com/docs/guides/local-development/cli/getting-started) (`brew install supabase/tap/supabase`)
- Docker Desktop running (for local dev via `supabase start`)
- `supabase login` once per machine (uses a personal access token from
  https://supabase.com/dashboard/account/tokens — not the DB password)
- The project is already linked in this repo (`supabase link --project-ref hhodoovjuqnmrmmdtrff`)

## Making a schema change

1. Write the change as a new migration:
   ```
   supabase migration new <short_description>
   ```
   This creates an empty timestamped SQL file under `supabase/migrations/`.
2. Write the SQL for your change in that file (e.g. `ALTER TABLE ... ADD COLUMN ...`).
3. Test it locally first:
   ```
   supabase start      # spins up local Postgres + Studio via Docker
   supabase db reset   # wipes local DB and reapplies all migrations from scratch
   ```
   Confirm the reset completes with no errors — this proves the migration is
   valid and reproducible before it ever touches production.
4. Apply it to production:
   ```
   supabase db push
   ```

## Pulling schema changes made manually in the dashboard

If someone edits the schema directly in the Supabase dashboard (should be
rare going forward), reconcile it back into a tracked migration:

```
supabase db pull --schema public
```

This diffs the live database against your local migration history and
writes a new migration file capturing the difference. Review the generated
SQL before committing it — introspection is not always perfect for every
constraint type.

## Verifying no drift

To confirm your local migrations exactly reproduce the live schema:

```
supabase db reset
supabase db diff --linked --schema public
```

`db diff` should report "No schema changes found" — any output means the
migration history and production have drifted apart.

## What's committed vs ignored

- **Committed**: `supabase/migrations/*.sql`, `supabase/config.toml`
- **Ignored** (`supabase/.gitignore`): `.branches`, `.temp`, local env files
- Migration files and `config.toml` contain schema/config only — no
  passwords, service role keys, or other secrets. `config.toml` references
  secrets via `env(VAR_NAME)` placeholders, never literal values.
